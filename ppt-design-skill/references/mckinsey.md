# 맥킨지 스타일 (컨설팅 덱 문법)

이력서·포트폴리오를 **제외한** 모든 유형의 기본값이다. 이력서는 이 문법이 맞지 않으므로 적용하지 않는다 — 이력서는 주장이 아니라 이력을 스캔시키는 문서다.

## 이 스타일의 정체

맥킨지 스타일은 색이나 폰트가 아니라 **논리 규칙**이다. 디자인만 흉내 내면 "네이비색 일반 PPT"가 나온다. 규칙은 셋이다.

1. **결론 먼저** — 배경부터 쌓아 올리지 않고 답을 먼저 말한 뒤 근거를 붙인다
2. **정보 제목과 핵심 메시지 분리** — 제목은 장의 내용을 식별하고, 리드문·키커가 주장과 해석을 전달한다
3. **MECE** — 근거는 서로 겹치지 않고 빠짐없이. 보통 3개

## 제목과 핵심 메시지 (가장 중요)

제목은 **짧은 명사형 정보 제목**을 기본으로 한다. `~한다`, `~이다`, `~할 수 있다`처럼 구어체 서술문으로 끝내지 않는다. 제목만 보고도 슬라이드가 다루는 대상과 범위를 바로 알 수 있어야 한다. 주장, 수치 해석과 결론은 제목 아래 리드문 또는 하단 키커에 분리한다.

| 피할 제목 | 좋은 제목 | 리드문·키커에 둘 메시지 |
|---|---|---|
| LLM 호출을 큐로 분리해 응답 지연을 줄였다 | 응답 지연 개선 결과 | 큐 분리 후 응답 지연이 3.0초에서 0.4초로 감소 |
| 이탈의 78%가 첫 설정 화면에서 발생한다 | 사용자 이탈 구간 분석 | 전체 이탈의 78%가 첫 설정 화면에서 발생 |
| 남은 리스크는 데이터 확보 하나다 | 잔여 리스크와 대응 계획 | 2월 내 데이터 계약으로 핵심 리스크 해소 예정 |
| 문제 정의 | 비정형 페이지 검수 문제 | 제작 시간의 60%가 수작업 검수에 투입 |

작성 기준:
- 한 줄을 우선하고 최대 2줄을 넘기지 않는다
- `Introduction`, `활동 목적`, `분과 활동`처럼 짧게 쓸 수 있으나, `소개`, `현황`처럼 대상이 없는 말은 피한다
- `~에 대하여`와 구어체 서술형 종결은 쓰지 않는다
- 제목만 읽어도 무엇을 설명·비교·검증하는 장인지 알아야 한다
- 숫자는 제목보다 리드문·키커에 배치해 제목의 식별성을 유지한다
- 사용자가 문장형 제목을 명시적으로 요구한 경우에만 예외로 한다

## 수평 논리 검사 (반드시 수행)

설계서를 사용자에게 보여주기 전에 두 번 검사한다. 먼저 **제목만 1번부터 읽어** 주제의 전개가 파악되는지 확인한다. 다음으로 각 장의 **핵심 메시지 또는 키커를 순서대로 이어 읽어** 하나의 완결된 주장이 되는지 확인한다. 중간에 "그래서?"가 튀어나오면 구조가 잘못된 것이다. 이 검사를 통과 못 한 설계서는 내보내지 않는다.

통과 예시(과제 발표):
> 점자도서관은 제작 시간의 60%를 수작업 검수에 쓴다 → 원인은 표·수식이 섞인 비정형 페이지에서 OCR 신뢰도가 급락하기 때문이다 → 우리는 신뢰도를 시각화해 검수 지점을 좁히는 방식을 택했다 → 그 결과 검수 대상 페이지가 100%에서 23%로 줄었다 → 남은 한계는 손글씨 페이지이며 별도 처리가 필요하다

## 도입부: SCR

앞 2~3장은 상황–문제–해결 순으로 짠다. 배경 설명을 길게 깔지 않는 장치다.

- **S(상황)**: 상대가 이미 동의하는 사실 한 문장
- **C(문제)**: 그런데 무엇이 어긋났는가 — 여기가 발표의 진짜 시작점
- **R(해결)**: 그래서 우리의 답은 무엇인가 → 이게 곧 핵심 요약 슬라이드

## 슬라이드 해부학

모든 본문 슬라이드는 같은 골격을 갖는다. 이 반복이 통일성을 만든다.

```
┌──────────────────────────────────────────┐
│ 섹션 트래커                        3 / 12 │  상단 얇게
├──────────────────────────────────────────┤
│ 정보 제목 — 이 장의 대상과 범위를 명사형으로 │  28px, 아래 실선
├──────────────────────────────────────────┤
│                                           │
│   근거 영역 (차트 · 도식 · 3열 근거)       │  텍스트 최소
│                                           │
├──────────────────────────────────────────┤
│ ▸ 키커: 그래서 무엇을 의미하는가          │  So-what 한 줄
│ 출처: ...                                 │  11px 회색
└──────────────────────────────────────────┘
```

키커(하단 한 줄)는 맥킨지 덱의 특징이다. 차트가 보여주는 것이 아니라 **차트가 의미하는 것**을 쓴다. "매출이 증가했다"(관찰)가 아니라 "성장이 온라인 채널 하나에 의존하고 있어 취약하다"(해석).

## 레이아웃 8종

| 이름 | 용도 |
|---|---|
| `cover` | 표지 |
| `exec-summary` | 핵심 요약 — 결론 1 + 근거 3. 3번째 장 안에 반드시 등장 |
| `tracker` | 섹션 구분. 전체 목차를 띄우고 현재 섹션만 강조 |
| `evidence` | 정보 제목 + 근거 3열 + 키커 (가장 많이 쓰는 기본형) |
| `chart` | 차트 좌 + 해석 우 + 키커 |
| `matrix` | 2×2 포지셔닝, 대안 비교 |
| `process` | 셰브론 단계 흐름, 파이프라인, 일정 |
| `compare` | before/after, 대안 A·B·C 표 |

## 차트 규칙

- 색은 **회색 계열 + 강조 1색**. 강조색은 말하려는 데이터 계열 하나에만 칠한다
- 범례 대신 **데이터 라벨을 계열 옆에 직접** 붙인다
- 격자선·테두리·그림자·3D 제거. 축 선도 최소화
- 별도 차트 제목은 넣지 않는다 — 슬라이드 정보 제목이 그 역할을 한다
- 출처 라인은 항상 왼쪽 하단에

## 색 프리셋 (맥킨지 계열 3안)

```
A. 딥네이비 — 정석. 제출·심사용 기본값.
   bg #FFFFFF / text #051C2C / accent #2251FF / muted #C8CDD3

B. 모노+레드 — 흑백에 강조 하나. 데이터가 많고 대비가 필요할 때.
   bg #FFFFFF / text #1A1A1A / accent #C8102E / muted #D4D4D4

C. 다크네이비 — 화면 공유·온라인 발표용.
   bg #051C2C / text #FFFFFF / accent #00A9F4 / muted #3A5060
```

강의실 프로젝터는 A·B, 화면 공유는 C가 안전하다.

## 하지 말 것

- 구어체 서술문으로 끝나는 제목
- 대상 없이 `소개`, `현황`, `결과`만 적은 모호한 제목
- 근거 5개 이상 나열 — 3개로 묶어라. 못 묶으면 MECE가 아니다
- 키커에 관찰만 쓰기. "그래서 무엇"이 없으면 키커가 아니다
- 아이콘·일러스트·그라데이션·둥근 모서리 남용. 이 스타일은 장식이 없는 게 특징이다
- 강조색을 두 군데 이상 쓰기
- 결론을 마지막 장에 두기. 결론은 앞에 한 번, 끝에 한 번

## 주의

이 문법은 **주장을 설득하는 자리**에 최적화돼 있다. 공모전 심사, 프로젝트 발표, 보고서에는 잘 맞는다. 다만 가벼운 동아리 활동 공유나 친목성 발표에 그대로 쓰면 과하게 느껴질 수 있으니, 그런 맥락이면 정보 제목과 핵심 키커는 유지하되 트래커·출처 라인 같은 격식은 빼는 편이 낫다.
