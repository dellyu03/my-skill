# 프로젝트·과제 발표

수업 텀 프로젝트, 캡스톤 중간·최종 발표, 팀플 결과 발표에 적용한다.

## 평가자가 실제로 보는 것

교수·조교는 아이디어의 참신함보다 **"이 사람이 직접 했는가"와 "왜 그렇게 결정했는가"**를 본다. 학부 발표에서 점수가 갈리는 지점은 거의 항상 이 셋이다.

1. 의사결정 근거 — 기술 선택에 이유가 있는가, 아니면 튜토리얼을 따라간 것인가
2. 검증 — 되는 걸 보여줬는가, 된다고 말만 했는가
3. 기여 분리 — 팀에서 본인이 뭘 했는지 드러나는가 (팀 발표여도 질의응답에서 갈린다)

그래서 **막힌 지점과 해결 과정이 최고의 재료**다. 초보 발표는 이걸 숨기고 성공한 결과만 보여주는데, 그러면 평가자 눈에는 "쉬운 걸 했다" 또는 "베꼈다"로 보인다.

## 표준 순서

`mckinsey.md` 의 피라미드 구조를 따른다. 학부 발표의 기본형(배경→과정→결과)과 가장 크게 다른 점은 **결과를 3번째 장에서 이미 말한다**는 것이다. 교수·심사위원은 시간이 없고, 결론을 먼저 들은 뒤 근거를 검증하는 방식으로 듣는다.

| # | 슬라이드 | 레이아웃 | 목적 |
|---|---------|---------|------|
| 1 | 표지 | cover | |
| 2 | 문제 (S–C) | evidence | 합의된 상황 한 줄 + 무엇이 어긋났는가. 일반론 금지, 구체적 상황으로 |
| 3 | **핵심 요약** | exec-summary | 우리가 뭘 만들었고 결과가 어땠는지를 **여기서 이미 말한다** + 근거 3축 |
| 4 | 목표와 범위 | evidence | 무엇을 했고 **무엇은 안 했는지**. 범위 명시가 "이건 왜 없냐" 질문을 막는다 |
| 5 | 전체 구조 | process | 시스템 한 장 요약. 이 장이 없으면 뒤 설명이 전부 붕 뜬다 |
| 6-8 | 핵심 구현 2~3개 | evidence / compare / process | **장당 하나의 기술적 의사결정**. 문제 → 대안 → 선택 이유 → 결과 |
| 9 | 검증·결과 | chart | 정량 지표. 없으면 최소한 before/after |
| 10 | 한계와 회고 | evidence | 솔직할수록 점수가 오른다. 아는 한계는 감점이 아니라 가점이다 |
| 11 | 마무리 | divider 또는 evidence | 3번 핵심 요약의 결론을 다시 한 번 + 질의응답 |
| 부록 | 코드·상세 스펙·추가 실험 | 자유 | 질문 대비용. 본문에서 빼되 준비는 해둔다 |

대안 비교(왜 A 대신 B를 썼는가)는 `compare`, 파이프라인·단계 흐름은 `process`, 그 외 근거 나열은 `evidence` 를 기본으로 쓴다.

## 분량 배분

**구현 + 검증에 전체의 50~60%.** 배경·동기는 20%를 넘기지 않는다. 학부 발표에서 가장 흔한 실패가 배경 설명 5장, 구현 2장이다. 평가자는 배경을 이미 안다.

발표 시간별 권장 장수 (분당 1~1.5장, 부록 제외):
- 5분 → 8장
- 10분 → 12~15장
- 15분 → 18~20장

## 강조할 것

- **의사결정 근거**: "A 대신 B를 썼다" 가 아니라 "A는 X 때문에 안 됐고, B로 바꾸니 Y가 해결됐다"
- **정량 결과**: 응답시간, 정확도, 처리량, 에러율. 절대값보다 **변화폭**이 설득력 있다
- **트러블슈팅**: 가장 오래 막혔던 문제 하나를 제대로 보여준다. 이게 실력의 증거다
- **시연**: 가능하면 GIF/스크린샷. 라이브 데모는 장비 사고 대비해 녹화본을 부록에 둔다

## 빼야 할 것

- 팀원 소개 슬라이드 (역할은 표지 하단 한 줄로 충분)
- 기술 스택 로고 나열 — 정보량이 없다. 아키텍처 다이어그램 안에 이름으로 넣으면 된다
- "AI 시대가 도래했습니다" 류의 일반론 도입부
- 향후 계획 남발. 안 한 일을 길게 쓰면 한 일이 적어 보인다. 한 장에 3줄이면 충분
- 코드 전문 스크린샷. 핵심 10줄만, 그것도 꼭 필요할 때만

## 중간발표일 경우

최종과 순서가 다르다. 평가자의 관심이 "결과"가 아니라 "계획이 현실적인가"에 있다.

- 목표·범위와 **일정·리스크**를 앞으로 당긴다
- 미완성인 것을 숨기지 않고 현재 진척도(%)와 남은 작업을 명시한다
- 검증 결과 대신 **검증 계획**(어떤 지표로 성공을 판단할 것인가)을 넣는다

## 디자인 프리셋

`mckinsey.md` 의 A(딥네이비) / B(모노+레드) / C(다크네이비) 중에서 고르게 한다. 강의실 프로젝터 발표면 A·B, 화면 공유면 C가 안전하다. 어느 쪽인지 모르면 물어본다.

과제·캡스톤 발표의 기본값은 A다. 데이터와 차트가 슬라이드의 절반 이상을 차지하면 B가 더 읽힌다.
