# 이력서·포트폴리오

## 맥킨지 스타일을 적용하지 않는다

이 문서 유형만 예외다. 이유는 **읽는 방식이 근본적으로 다르기 때문**이다.

- 컨설팅 덱: 발표자가 **하나의 주장을 설득**한다 → 정보 제목, 수평 논리, 핵심 키커가 작동한다
- 이력서: 채용 담당자가 **6~10초 만에 거를지 판단**하려고 스캔한다 → 설득 구조가 아니라 **검색 구조**가 필요하다

이력서에 "저는 데이터 파이프라인 최적화로 처리 시간을 40% 줄였습니다" 같은 문장형 주장을 크게 쓰면, 정작 스캔하는 사람이 찾는 회사명·기간·기술 스택이 안 보인다. 그래서 컨설팅 덱의 정보 제목·키커·트래커 문법을 그대로 쓰지 않는다.

## 이력서의 문법

**스캔 경로를 설계한다.** 사람 눈은 왼쪽 위에서 시작해 F자로 훑는다. 그 경로에 이름 → 한 줄 요약 → 최근 경력 → 기술 스택이 순서대로 놓이게 한다.

**역순 연대기.** 최신이 위. 예외 없다.

**한 항목당 불릿 3개 이내**, 각 불릿은 `무엇을 + 어떻게 + 결과(숫자)` 형태로 쓴다.

> 팀 프로젝트에서 백엔드를 담당했습니다 → 약함
> FastAPI 기반 추론 서버를 설계해 동시 요청 처리량을 3배(50→150 RPS)로 개선 → 강함

**기술 키워드를 그대로 쓴다.** 채용 담당자와 필터 시스템 모두 키워드로 찾는다. "클라우드 환경"이 아니라 "AWS EC2, S3, RDS".

**링크는 상단에.** GitHub, 기술 블로그, 배포된 서비스. 신입일수록 여기서 갈린다.

## 포트폴리오 PPT의 문법

이력서와 또 다르다. 이력서가 스캔용이라면 포트폴리오는 **증거물**이다.

- **프로젝트당 1~2장.** 5개를 얕게 보여주는 것보다 2~3개를 제대로 보여주는 게 낫다
- 장 구성: **문제 → 내 역할 → 기술적 선택과 이유 → 결과(숫자) → 결과물 스크린샷**
- **내 기여를 반드시 분리한다.** 팀 프로젝트라면 "팀 4명 중 백엔드·인프라 담당"처럼 명시. 이게 없으면 전부 본인이 한 것처럼 보이고, 면접에서 무너진다
- 결과물 스크린샷이나 데모 GIF를 크게. 동작하는 것의 증거가 설명보다 강하다
- 코드는 핵심 10~20줄만, 그것도 설명할 가치가 있을 때만

## 빼야 할 것

- 사진·자기소개·취미 (국내 개발 직군 기준 대부분 불필요)
- 기술 스택 숙련도 별점·프로그레스 바 — 주관적이고 신뢰를 얻지 못한다
- 수강 과목 나열 (프로젝트로 증명한다)
- "열정", "성실", "빠르게 배웁니다" 같은 형용사. 전부 증거로 대체한다

## 디자인

`mckinsey.md` 프리셋을 쓰지 않는다. 이력서는 **흰 배경 + 검정 본문 + 강조 1색**이 안전하다. PDF로 출력했을 때, 그리고 흑백 인쇄했을 때 읽히는지 반드시 확인한다.

- 여백을 넉넉히. 꽉 채운 이력서는 읽히지 않는다
- 서체 1종, 크기 3~4단계로 충분
- 슬라이드형 포트폴리오는 1280×720 유지, 문서형 이력서는 A4 세로

## 전용 골격이 아직 없다

`assets/mckinsey-slides.html` 은 맥킨지 레이아웃 전용이라 이력서에 맞지 않는다. 이 유형은 골격을 새로 짜되, 위 원칙(스캔 경로, 역순, 숫자 불릿, 흰 배경)을 지킨다. 사용자에게 **전용 템플릿이 아직 없다는 점을 알린다.**
