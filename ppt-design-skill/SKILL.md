# PPT Design

## 이 스킬이 푸는 문제

AI로 만든 발표자료가 실패하는 이유는 두 가지이고, 원인이 서로 다르다.

1. **목적을 모른다.** 공모전 심사위원과 과목 교수는 다른 것을 본다. 공모전은 "왜 필요하고 남들과 뭐가 다른가"를, 과제 발표는 "직접 했고 왜 그렇게 결정했는가"를 본다. 같은 프로젝트라도 순서와 분량 배분이 달라져야 한다. → 아래 용도별 표와 `references/` 문서로 해결한다.
2. **디자인과 논리를 매번 새로 생성한다.** 그래서 뒤죽박죽이 된다. → 논리는 문법으로, 디자인은 **고정 토큰 + 정해진 레이아웃**으로 자유도를 없앤다.

## 만드는 것 / 만들지 않는 것

**만드는 것**
- 슬라이드별 메시지가 확정된 **설계서** (텍스트)
- 그 설계를 실제 디자인으로 보여주는 **레퍼런스 슬라이드 3장** (단일 HTML)

**만들지 않는 것**
- 20장짜리 완성 덱. 토큰만 쓰고 어차피 전부 고쳐야 한다. 사용자가 레퍼런스 3장을 복제해 채우는 편이 빠르다. 명시적으로 전체 생성을 요구할 때만 예외로 한다.

## 워크플로우

### 1단계 — 브리프 확보 (묻기 전에 추론한다)

질문 공세가 가장 성가신 실패다. 순서는 **추론 → 기본값 제시 → 확인**이다.

1. 대화·파일·기억에서 용도를 먼저 추론한다. "과제 발표", "공모전 제출", "동아리 결산", "연구 요약" 같은 단어 하나면 아래 표로 나머지가 거의 결정된다.
2. 추론한 용도의 기본값(평가자·시간·장수·형식·톤)을 **한 줄로 요약해 제시하고** 다르면 알려달라고 한다. 백지 상태로 다섯 개를 묻지 않는다.
3. 기본값으로 메울 수 없는 것만 묻는다. 대개 둘뿐이다 — **발표 시간**(또는 장수 제한)과 **심사표·평가 기준의 존재 여부**.
4. 담을 내용이 없으면 그때 받는다. 프로젝트 관련 기억이나 업로드 파일이 있으면 먼저 찾아본다.

용도를 끝내 알 수 없을 때만 직접 묻는다.

## 용도별 기본값과 강조점

| 용도 | 평가자가 보는 것 | 통상 조건 | 최우선 강조 | 대표 감점 요인 | 톤 | 문서 |
|---|---|---|---|---|---|---|
| **수업 과제·텀 프로젝트** | 직접 했는가, 왜 그렇게 결정했는가 | 7~10분 발표, 10~15장 | 의사결정 근거, 트러블슈팅, 정량 검증 | 배경 과다, 팀원 소개, 스택 로고 나열 | 컨설팅형 | `project.md` |
| **캡스톤 중간발표** | 계획이 현실적인가 | 10분, 12~15장 | 진척도(%), 리스크와 대응, 검증 **계획** | 미완성 숨기기, 장밋빛 일정 | 컨설팅형 | `project.md` |
| **캡스톤 최종·졸업작품** | 완성도와 실사용 가능성 | 15분 + 시연, 18~20장 | 동작하는 결과물, 개인 기여 분리 | 시연 실패 대비 없음, 기여 불명확 | 컨설팅형 | `project.md` |
| **공모전·경진대회** | 남들과 뭐가 다르고 진짜 되는가 | 5~7분 발표 또는 15~20장 PDF | 차별성, 실현가능성, 기대효과 정량화 | 기술 상세 과다, 근거 없는 시장규모 | 컨설팅형 | `contest.md` |
| **해커톤** | 짧은 시간에 뭘 만들었나 | 3~5분, 8장 이내 | 동작 데모 먼저, 만든 범위 명확히 | 기획만 있고 결과물 없음 | 컨설팅형 | `contest.md` |
| **동아리 활동 보고서** | 목표 대비 달성과 지속 가능성 | 읽는 자료, 장수 자유 | 숫자(인원·횟수·참여율·예산), 다음 학기 계획 | 사진 나열, 감상문, 회계 불투명 | 둘 다 가능 | `report.md` |
| **연구·리서치 보고서** | 혼자 읽어도 이해되는가 | 읽는 자료, 6~10장 | 방법·데이터 출처, 결과 해석, 한계 | 발표 전제로 쓴 빈약한 슬라이드 | 연구보고서형 | `tone-research.md` |
| **이력서·포트폴리오** | 6~10초 스캔으로 거를지 말지 | 읽는 자료 | 역할·기여·성과 수치, 링크 | 발표자료 문법을 그대로 적용하는 것 | 전용 | `resume.md` |

**형식이 강조점을 바꾼다.** 발표용은 장당 40단어 상한에 구두 설명이 절반을 채우지만, 제출·심사용은 발표자가 없으므로 장당 100단어까지 올리고 슬라이드만으로 논리가 닫혀야 한다. 어느 쪽인지 모르면 이것만은 반드시 묻는다.

## 2단계 — 톤과 문서 결정

톤은 두 가지이고, **섞지 않는다.** 둘은 설계 철학이 반대여서 섞으면 양쪽 다 무너진다.

| 톤 | 성격 | 맞는 곳 | 문서 | 골격 |
|---|---|---|---|---|
| **컨설팅형** | 명사형 정보 제목, 장당 메시지 1개, 장식 제거 | 발표해서 설득하는 자리 | `references/mckinsey.md` | `assets/mckinsey-slides.html` |
| **제안서형** | 목차·섹션 구분·번호 마커, 구성의 완결성 | 15장 이상으로 전 구간을 훑는 자리 | `references/tone-proposal.md` | `assets/proposal-slides.html` |
| **연구보고서형** | 중앙정렬 제목, 카드 그리드, 민트/딥틸, 높은 정보 밀도 | 혼자 읽는 자료 | `references/tone-research.md` | `assets/research-slides.html` |

**판단은 두 단계다.**

1. **발표자가 옆에 있는가.** 없으면 연구보고서형으로 끝난다.
2. 있다면 **분량을 본다.** 10장 이내로 하나의 주장을 밀어붙이는 자리면 컨설팅형, 15장 이상으로 목차부터 기대효과까지 빠짐없이 훑어야 하면 제안서형이다.

심사위원이 체크리스트를 들고 항목별로 채점하면 제안서형, 하나의 결론을 납득시켜야 하면 컨설팅형이다. 12~14장 구간이면 **심사표 유무로 가른다.**

발표 후 자료를 남기는 경우는 발표 쪽 톤(컨설팅형 또는 제안서형)으로 만들고 부록을 두껍게 한다.

톤을 정한 뒤 해당 톤 문서와 위 표의 용도 문서를 **함께** 읽는다. 톤 문서가 색·타입·레이아웃을, 용도 문서가 순서·강조를 결정한다.

**절충이 필요할 때.** 시각은 연구보고서형인데 논리는 설득이어야 하는 경우(예: 심사용 연구 포스터)가 있다. 이때는 제목을 명사형 정보 제목으로 좌측 정렬하고, 하단 띠 자리를 핵심 메시지용 키커로 쓴다. 대신 **정보 밀도를 낮춘다** — 카드 8개에 하나의 해석 문장을 붙이면 그 문장이 어느 근거를 가리키는지 알 수 없다. 절충은 사용자가 요청했거나 명백히 필요할 때만 하고, 기본은 한쪽을 고르는 것이다.

여기 없는 유형(학회 발표, 사내 보고 등)이면 가장 가까운 문서로 대응하되, **"이 유형 전용 가이드는 아직 없다"고 밝힌다.** 없는 지식을 있는 척 적용하는 것이 가장 나쁘다.

## 3단계 — 설계서를 먼저 승인받기

디자인보다 논리가 먼저다. 다음 표를 대화에 출력하고 확인받는다.

```
| # | 레이아웃 | 제목 | 핵심 메시지 | 근거·자료 |
|---|---------|------|-------------|----------|
| 1 | cover   | —    | —           |          |
```

**제목은 기본적으로 구어체 문장이 아닌 명사형 정보 제목으로 쓴다.** `Introduction`, `활동 목적`, `분과 활동`, `시스템 아키텍처`, `사용자 조사 결과`처럼 제목만 보고도 슬라이드의 범위와 내용을 바로 알 수 있어야 한다. `~한다`, `~이다`, `~할 수 있다`처럼 서술형 종결을 제목에 쓰지 않는다. `소개`, `현황`처럼 지나치게 넓은 말만 단독으로 쓰지 말고 대상을 붙인다. 예: `소개`가 아니라 `Temp0.7 활동 개요`, `현황`이 아니라 `2026년 2학기 운영 일정`.

주장, 수치 해석과 결론은 제목 아래 리드문 또는 하단 키커에 분리한다. 예: 제목은 `응답 지연 개선 결과`, 리드문은 `큐 분리 후 응답 지연이 3.0초에서 0.4초로 감소`로 쓴다. 사용자가 문장형 제목을 명시적으로 요구한 경우에만 예외로 한다. 세부 기준은 `mckinsey.md` 의 제목 절을 따른다.

**컨설팅형은 출력 전 수평 논리 검사를 반드시 한다.** 제목 순서만 읽어도 주제 전개가 파악되는지 확인하고, 각 장의 핵심 메시지나 키커를 이어 읽었을 때 하나의 완결된 주장이 되는지 확인한다. 중간에 논리가 끊기면 구조를 고친 뒤 내보낸다. 검사 결과를 한 줄로 알린다.

연구보고서형은 수평 논리 대신 **자립성**을 검사한다. 각 장이 발표자 설명 없이 혼자 읽혀야 하고, 그렇지 않은 장은 리드문이나 캡션을 보강한다.

## 4단계 — 색 프리셋 제안

톤 문서의 프리셋 중 맥락에 맞는 2~3개를 **한 줄 설명 + hex**로 제시하고 고르게 한다. 이미지로 비교시키지 않는다 — 토큰 낭비다. 선택된 프리셋은 덱 전체에 고정되며, 이후 슬라이드마다 색을 바꾸지 않는다.

- 컨설팅형: `mckinsey.md` 의 A 딥네이비 / B 모노+레드 / C 다크네이비
- 제안서형: `tone-proposal.md` 의 A 인디고(기본) / B 청회색 / C 코발트+크림 / D 퍼플 / E 다크 일렉트릭. 정하기 애매하면 A를 쓴다. E는 인쇄하면 무너지므로 PDF 제출 겸용이면 제안하지 않는다
- 연구보고서형: `tone-research.md` 의 민트·딥틸이 기본. 다른 색으로 옮기려면 `--accent` 계열 3단계를 같은 명도 간격으로 다시 잡는다

## 5단계 — 레퍼런스 슬라이드 3장 생성

해당 톤의 골격 파일을 복사해 3장만 만든다.

**컨설팅형**: 표지 / 핵심 요약(exec-summary) / 본문 대표 1장(evidence 또는 chart)
**제안서형**: 표지 / 목차 / 본문 대표 1장(`l-numbered` 또는 `l-cards-grid`)
**연구보고서형**: 표지 / 개요형 3열 카드 / 요약·상세형

제안서형은 장수가 많은 톤이라 섹션 디바이더를 물어볼 가능성이 높다. 3장에는 넣지 말고, `l-divider` 가 골격 파일에 있으니 복제해 쓰면 된다고 전달할 때 한 줄로 알린다.

전달할 때 함께 알릴 것: 나머지 장은 이 3장을 복제해 채우면 된다는 점, 색·폰트는 파일 최상단 `:root` 블록만 고치면 된다는 점.

## 디자인 규칙 (고정, 협상 불가)

이 제약이 "AI 만든 티"와 뒤죽박죽을 막는 핵심이다. 톤별 세부 수치는 각 톤 문서에 있다.

**색** — 톤 문서에 정의된 팔레트만 쓴다. 강조색은 덱 전체에서 한 가지 의미로만 쓴다. 여기저기 칠하면 아무것도 강조되지 않는다.

**타입** — 서체 2종 이하. 크기는 톤 문서의 단계만 쓰고 중간값을 즉흥적으로 만들지 않는다. **한글 자료는 Pretendard로 통일한다** — 영문 전용 서체(Libre Franklin 등)는 한글 글리프가 없어 시스템 폰트로 대체되고 자간·굵기가 어긋난다.

**제목** — 기본은 명사형 정보 제목이다. 구어체 서술문으로 끝내지 않고, 한 줄을 우선하며 최대 2줄을 넘기지 않는다. 제목만 읽어도 `무엇에 관한 장인지` 알 수 있어야 한다. 주장과 해석은 리드문 또는 키커에 둔다.

**간격** — 8px 배수만.

**레이아웃** — 톤 문서에 정의된 것만 사용한다. 새 레이아웃을 즉석에서 만들지 않는다.

**공통 금지**
- 슬라이드마다 다른 강조색
- 정보량 없는 장식 (기술 스택 로고 그리드, 의미 없는 아이콘 나열, 그라데이션 장식)
- 한 장에 문단 통째로 붙여넣기
- 순서가 아닌 것에 `01 / 02 / 03` 마커 붙이기
- 두 톤의 요소 혼용 (컨설팅형 슬라이드에 둥근 카드, 연구형에 키커 바 등)

**제안서형 예외.** 아래 셋은 제안서형에서만 허용한다. 다른 두 톤에서는 그대로 금지다.
- 병렬 항목에 `01 / 02 / 03` 번호 마커 (순서가 아니어도 됨)
- 가장자리 분위기 장식 (손그림 화살표, 원형·부채꼴 도형) — 콘텐츠 영역은 침범하지 않는다
- 카드별 아이콘 — 의미가 구분될 때만

## HTML 골격 규칙

수정 비용을 낮추는 것이 이 형식을 고른 이유다.

- 모든 디자인 값은 최상단 `:root` CSS 변수에 모은다. 색 변경 요청이 변수 몇 줄 교체로 끝나야 한다
- 슬라이드 하나 = `<section class="slide ...">` 하나. 클래스가 스타일을 결정하므로 복제해도 디자인이 유지된다
- 인라인 style 속성 금지. 단 하나의 예외는 차트 막대 길이 같은 **데이터 수치**(`style="width:47%"`)다
- 1280×720 고정 캔버스, 화면에서는 `transform: scale()` 로 맞춘다
- 외부 CDN·폰트 로드 없이 동작해야 한다

## 산출 형식

기본은 HTML이다. 브라우저 인쇄로 PDF가 바로 나오고, 제출용은 대개 PDF면 충분하다.

`.pptx` 파일이 필요하다고 하면 그때 변환한다. 이때 컨설팅형의 **제목 밑 실선과 키커 색 바는 의도된 문법**이므로, 일반적인 "장식선을 쓰지 말라"는 슬라이드 제작 지침보다 이 스킬의 규칙이 우선한다. 변환 후에는 반드시 렌더 이미지를 확인해 텍스트 넘침과 한글 폰트 대체를 점검한다.

## 수정 요청 처리

- "색/분위기 바꿔줘" → `:root` 변수만 교체, 마크업은 건드리지 않는다
- "이 장 구성 바꿔줘" → 해당 `section` 의 레이아웃 클래스를 톤 문서의 목록 중 다른 것으로 교체
- "장 추가" → 기존 장을 복제해 내용만 교체. 새 스타일을 만들지 않는다
- "제목이 밋밋하다" → 구어체 문장으로 늘리지 않는다. 대상과 범위를 구체화한 명사형 정보 제목으로 다시 쓴다. `mckinsey.md` 의 대조표를 따른다
- "전체 덱으로 만들어줘" → 이때만 설계서 기준으로 전체를 생성한다

## 새 템플릿 추가 (톤 확장)

사용자가 디자인 템플릿(이미지, PPT, PDF, HTML 등)을 올리고 "이 템플릿도 추가해줘" 같은 요청을 하면, 원본을 그대로 복제하지 않고 이 스킬의 고정 형식(:root 토큰 + section 골격)에 맞게 변환해 등록한다.

1. **토큰 추출** — 템플릿에서 색상 팔레트(hex), 서체, 여백·간격 체계, 제목 위치, 카드/그리드 여부 등 반복되는 레이아웃 패턴을 읽어낸다.
2. **기존 톤과 비교** — 컨설팅형·제안서형·연구보고서형 중 하나의 변형인지, 완전히 새로운 네 번째 톤인지 판단해 사용자에게 한 줄로 확인받는다.
3. **기존 톤의 변형이면** 해당 `references/*.md`에 새 색상 프리셋으로 추가하고, 필요하면 골격 파일(`assets/*.html`)에 레이아웃 변형만 더한다. 골격 규칙(1280×720 고정, `:root` 변수, 슬라이드 하나 = `section` 하나, 인라인 style 금지, 외부 CDN 없음)은 그대로 지킨다.
4. **새로운 톤이면** `references/tone-{이름}.md`를 기존 톤 문서와 같은 구조(팔레트 · 타이포 단계 · 레이아웃 목록 · 금지 사항)로 작성하고, `assets/{이름}-slides.html` 골격 파일에 표지·핵심 슬라이드 등 3장을 채운 뒤, 이 문서의 2단계 톤 표와 필요하면 용도별 표에도 새 행을 등록한다.
5. **원본 보관** — 업로드된 원본 파일은 참고용으로 `assets/samples/`에 두고, 실제 제작에는 토큰화된 버전만 쓴다.
6. **검증** — 변환 결과가 "디자인 규칙 (고정, 협상 불가)" 절(서체 2종 이하, 8px 배수 간격, 강조색 단일 의미 등)을 만족하는지 원본과 대조하고, 어긋나면 규칙 쪽을 우선해 조정한다.

## 참고 자료
